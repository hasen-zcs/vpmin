# 核心检测模块详解

> 对象：`vpmin/domain/` + `vpmin/adapters/{probe,roi,painter}.py` + `vpmin/runner.py`
> 目标：读完这份文档，能独立改判据、调参数、定位现场问题。

---

## 1. 一句话说清它干什么

从摄像头里**只看一块 ROI（球化反应区）**，逐帧统计灰度，判断「球化亮光什么时候开始、什么时候结束、中间断没断」，
最后落一条记录：**时长 + 与标准区间的比较结果 + 分段明细**。

它**不判断**"这炉好不好"这种业务结论——只产出可核对的客观量：起止时刻、时长、段数、每段间隔。

---

## 2. 处理流水线（一帧的完整旅程）

```
摄像头帧
   │
   ▼
RoiProbe.measure()            取 ROI 灰度 → 三个数：mean_gray / start_pct / end_pct
   │                          （start_pct = 灰度 ≥ start_pixel 的像素占比 %）
   ▼
MedianFilter.apply()          因果中值（默认 5 帧）压毛刺，只用来喂状态机
   │                          原始值仍照旧进曲线/逐帧 CSV —— 不许改历史数据
   ▼
Thresholds.start_ok/end_ok    纯比较：start_pct ≥ 40%？end_pct ≥ 70%？
   │
   ▼
ReactionStateMachine.advance() 六态迁移 + 确认时长（start_confirm / end_confirm）
   │
   ├─ started → CurveBuffer.begin()（接上 5s 前置基线）+ 建段 + 杂光考察期
   ├─ ended   → 收段 + 关曲线 + 挂起等 merge_gap
   │
   ▼
_expire() / _commit()         merge_gap 到期 → 结算
   │
   ▼
judge(duration, window, segments, pause_threshold)   → Verdict(type 0/3/4/5/6)
   │
   ▼
CurvePainter.draw()          画曲线图（960×540 灰度）
   │
   ▼
JsonlSink.build()            7 字段（原契约）+ 追加 abnormal_type/reason/segments
```

关键约束：**domain 层不 import cv2 / numpy / urllib**，只吃数字吐结论。所以状态机、判据、区间策略全部可以脱机单测（12 万帧对拍就是这么跑的）。

## 3. 逐模块详解

### 3.1 `adapters/probe.py` — 像素统计（唯一碰 OpenCV 的地方）

```python
mean_gray  = ROI 内所有像素的算术平均
start_pct  = ROI 内 灰度 >= start_pixel 的像素占比 × 100
end_pct    = ROI 内 灰度 <= end_pixel   的像素占比 × 100
```

- **矩形 ROI**：直接切片 `gray[y:y+h, x:x+w].ravel()`
- **多边形 ROI**：`roi.mask(h, w)` 生成布尔掩膜，掩膜建成后按形状缓存（ROI 不变就不重复建）
- **ROI 落在画面外**：`pixels.size == 0` → 返回 `None`，本帧整条跳过（不污染状态机）
- 口径与生产原版 `engine.process` 逐像素一致，这是"对拍能过"的前提

> ⚠️ 为什么用"占比"而不是"平均灰度"：现场 ROI 里既有亮熔液也有暗背景，光照会整体漂移，
> 平均值跟着漂；而"有多少像素超过阈值"对整体亮度变化不敏感，只对"亮没亮起来"敏感。

### 3.2 `domain/models.py` — 五个冻结数据结构

| 结构 | 字段 | 用途 |
|---|---|---|
| `FrameMetrics` | elapsed / mean_gray / start_pct / end_pct | 一帧的测量值 |
| `Transition` | state / started / ended | 状态机推进结果 |
| `Window` | low / high / kind | 判定区间 + 来源（"后端上下限"/"后端标准值±容差"/"本地回退区间"/"无"） |
| `Segment` | start / end / gap_before | 一段连续亮光；`gap_before` = 距上一段的停顿秒数 |
| `Verdict` | duration / window / ok / abnormal_type / abnormal_reason / segments | 一次反应的最终判定 |

全部 `frozen=True`（不可变）。原因：判定结果一旦产出，下游（落盘、画图、上报）拿到的是快照，
不会因为后续帧继续推进而"悄悄变化"——这是排查现场纠纷时能对得上账的前提。

### 3.3 `domain/trigger.py` — 阈值比较（故意做到最小）

```python
start_ok(start_pct)  →  start_pct >= thresholds.start_pct   # 现场 40
end_ok(end_pct)      →  end_pct   >= thresholds.end_pct     # 现场 70
```

只有两个纯函数。把它独立出来的意义：**判"亮没亮"和判"算不算一炉"是两件事**，
前者是物理（灰度），后者是时序（确认窗口），混在一个类里就没法单独测。

### 3.4 `domain/state_machine.py` — 六态机（系统的时序心脏）

```
                  start_ok                    start_confirm 到点
   WAITING ──────────────────► CANDIDATE_START ──────────────────► STARTED
      ▲                              │                                  │
      │        start_ok 断了          │                                  │ end_ok
      └──────────────────────────────┘                                  ▼
                                                                  CANDIDATE_END
                                                                        │
                                             end_confirm 到点             │ end_ok 断了
                                    ENDED ◄──────────────────────────────┤
                                      │                                  │
                                      │ rearm()                          └──► STARTED
                                      ▼
                                  COOLDOWN ──（start_ok 消失）──► WAITING
```

三条必须记住的规则：

1. **确认时刻取"条件连续满足满 N 秒"的那一帧**，不是"第一帧满足"的那一帧。
   `start_t` 是确认帧的时刻 —— 所以 `start_confirm` 越大，起判越晚。这是 2026-10-29 那次
   「起判晚 76 秒」事故的直接机理（现场把 0.2 改成了 1.5）。
2. **CANDIDATE 状态"一掉就清零"**：`start_ok` 断一帧，`start_cond` 立刻置 None 退回 WAITING。
   现场 ROI 只有约 1000 px²，占比在阈值上下反复翻，所以 `start_confirm` 必须小（0.2s），
   容错要靠**中值滤波**而不是靠拉长确认窗口。
3. **ENDED 不自转**：停在原地等外部 `rearm()` 把它推到 COOLDOWN。
   COOLDOWN 的意义是迟滞——同一炉的"尾巴"（余辉、二次小峰）不会被当成第二次开始。

`advance()` 是纯函数式推进：输入 (now, start_ok, end_ok)，输出 Transition，不碰任何 I/O。
12 万帧对拍原版 `ReactionDetector` 零差异，就是靠这份纯净。

### 3.5 `domain/filter.py` — 因果中值滤波

```python
median_frames = 5    # 0 或 1 = 关闭
```

- **因果**：只用过去 N 帧，不看未来 → 实时可实现，且不会"提前知道结局"
- 对 `start_pct` / `end_pct` 分别取中值，喂给状态机；**原始值仍照旧进曲线和逐帧 CSV**
- 实测收益（2026-10-29 模拟）：
  - 真实数据上起判只偏 **+0.09s**、结束 **+0.16s**、时长 **+0.07s**（可忽略）
  - 丢帧 20% 时起判最坏推迟 **19.2s → 6.7s**；丢帧 30% 时 **40.3s → 19.2s**
  - 安静段无误起判；50 炉判定零翻转

> ⚠️ 同一轮实验里，"滑窗比例法"（N 秒窗口内 K% 像素达标才算亮）是**负收益**：
> 1.0s/60% 起判晚 19.7s，1.5s/50% 晚 30s。**不要再用滑窗**，参数一长就是灾难。

### 3.6 `domain/curve.py` — 曲线缓冲

- `preroll=5.0`：总是保留最近 5 秒的点，起判时 `begin()` 把它们接到曲线前面 → 图上有"起跳前"的基线
- `begin()` / `close()` / `view()`：开始接点 / 结束定稿 / 给页面看（进行中优先，结束后留上一条）
- **`resume()`（断点续接专用）**：把上一段曲线接回来继续画，并把间隙期间的前置点补在后面。
  所以合并后的落盘图是**完整一条**（含中间那段凹陷），不是只剩后半截
- 超长反应（>20000 点）隔点抽稀，保留首尾，防止内存爆掉

### 3.7 `domain/standard.py` — 三级区间回退

```
① 后端给了上下限 → [lower, upper]（写反自动摆正；只给一边视为没给）
② 只给标准值     → [value - tolerance, value + tolerance]
③ 都没有         → 本地 settings.json 的 standard_min / standard_max
```

- **取失败不清缓存**：`update(ok=False)` 只加失败计数，`payload` 原样保留。
  网络抖一下不该让判定结论翻转
- `ttl` + `fresh()`：给状态页显示"标准是不是新鲜的"
- **断开后端 = 不传 `--biz-url`**，此时 `standard_feed=None`，直接落到 ③ 本地区间。
  这是做 A/B 验证（本地 60~120 vs 后端 60~90）而不影响生产的最干净做法

### 3.8 `domain/judge.py` — 判定（3/4/5）

```python
TYPE_NORMAL   = 0
TYPE_OVER     = 3   # 超过标准
TYPE_UNDER    = 4   # 低于标准
TYPE_PAUSE    = 5   # 中间停顿
TYPE_UNJUDGED = 6   # 未判定（缺时长或缺标准）
```

判定顺序（**单列只能写一个类型码，所以必须有优先级**）：

```
1) pause_threshold > 0 且 段数 ≥ 2 且 最大停顿 > 阈值   → 5 中间停顿
2) duration > high                                   → 3 超过标准
3) duration < low                                    → 4 低于标准
4) 否则                                              → 0 正常
```

三条硬口径（2026-10-29 定）：

- **判定时长 = 亮光时长 = 首段起 → 末段止（含中间停顿）**，不是各段相加，也不做 PLC 换算
- **区间是闭区间**：`low <= duration <= high` 算正常
- **统一 `round(x, 3)`**：判定与显示同一套舍入（防止 `102.47999999999999` 这种脏值入库）

`longest_gap()` 返回的是**最长的那个停顿**以及它属于第几段（段序号从 1 起，指"停顿之后的那一段"）。
原因文案例如：

```
球化过程中间亮光停顿：第 3 段前停顿 42.633s
```

`_fmt()` 会去掉多余的 0（95.20 → "95.2"），纯粹为了原因文案好读。

### 3.9 `runner.py` — 编排层（最复杂的一个文件）

它是"一帧进 → 判定 → 落盘"的总调度，也是四条现场经验的落脚点：

#### (a) 断点续接 `merge_gap`

判到结束后**不立刻落盘**，先挂起 `merge_gap` 秒：

```
如果 merge_gap 内又判到开始：
    不新起序号、不改起点、曲线 resume() 接回来、结束时刻后移、记录多一段
如果超过 merge_gap 还没有新开始：
    _expire() → _commit() 落盘
```

现场意义：同一炉中间熄一下会被切成两条记录（一条 6.0s、一条 92.7s），
合并后回到 100.3s，终点误差从 −91.17s 修正到 +2.98s。

**但窗口不能大**：反应结束 8.66 秒后才冒出的开门杂光不该被合并（合并会把本来 +3.95s 的那炉搞成 +23.6s），
所以现场取 **5 秒**。

#### (b) 杂光考察期 `guard_window` / `guard_peak` / `min_duration`

起判后先观察 `guard_window` 秒（现场 3.0）：

```
考察期内峰值 < guard_peak（现场 80%）  → 判开门杂光：状态复位、序号 rollback、不落盘
考察期没跑完就结束了                    → 太短，同样丢弃
考核通过                                → guard 清空，按正常反应继续
```

再加一道 `min_duration`（现场 20s）：总时长不足也丢。

现场依据：开门杂光起判时占比只有 40.0~45.2%、灰度 131~183；正常炉 2~3 秒内必冲到 90%+、灰度 228。
124 万帧实测：5 条杂光全清、69 条正常反应零误杀。

#### (c) 分段与 segment 记录

段列表从**起判那一刻**就建好（`pending["segments"]`），结束/续接时往里填：

```python
{"start": ..., "end": ..., "gap_before": None}   # 第一段
{"start": ..., "end": ..., "gap_before": 42.6}   # 续接段，gap 由 start_t - 上段 end 算出
```

落盘时转成 `Segment` 元组，交给 `judge()`，同时把多段明细写进记录新增字段 `spheroidization_segments`。

#### (d) 时间轴

- `process(frame, elapsed)` 里的 `elapsed` 是**秒表秒**（从分析开始算）
- 落盘时用 `wall(base, t)` 换成墙钟；`base` 是分析起点
- **分段明细也必须换算**（`_extras` 里做），否则记录里的分段会显示成 1970 年（真踩过）

#### (e) 产出与取走分离

`process()` 不返回结果，写进 `_flushed`；分析循环每帧后调 `drain()` 取走。
好处：一轮帧处理里可能同时产出"上一条到期落盘"+"本帧新开始"，不会丢事件。

`flush_pending()`：停止分析 / 炉边界（PLC 到位、按钮）时，把还在合并窗口里的那条立刻落盘——
**不能因为停服务就丢一炉数据**。

## 4. 参数全表（现场必读）

| 参数 | 含义 | 现场值 | 调大 | 调小 |
|---|---|---|---|---|
| `start_pixel` | 亮像素阈值（灰度） | 180 | 更难判亮，起判晚 | 误判亮 |
| `end_pixel` | 暗像素阈值（灰度） | 180 | 更容易判暗，结束早 | 结束晚 |
| `start_threshold` | 开始占比阈值 % | 55 | 起判晚、漏短反应 | 误起判 |
| `end_threshold` | 结束占比阈值 % | 55 | 结束早 | 结束晚 |
| `start_confirm` | 开始确认秒数 | **0.2** | ⚠️ 极度敏感，1.5 会晚 76s | 抖动误起判 |
| `end_confirm` | 结束确认秒数 | 4.0 | 结束晚（时长变长） | 余辉误判结束 |
| `median_frames` | 中值滤波帧数 | 5 | 更平滑、更滞后 | 无滤波 |
| `merge_gap` | 断点续接窗口 s | 5.0 | 可能误并下一炉 | 一炉被切两段 |
| `pause_threshold` | 中间停顿判定 s | 10 | 只抓长停顿 | 抓得细但易误报 |
| `guard_window` | 杂光考察期 s | 3.0 | 判定更稳但出结论晚 | 杂光漏网 |
| `guard_peak` | 考察期峰值下限 % | 80 | 更严，正常炉可能被丢 | 杂光漏网 |
| `min_duration` | 最短有效时长 s | 20 | 更严 | 杂光漏网 |
| `standard_min/max` | 本地回退区间 | 60 / 120 | — | — |
| `preroll` | 曲线前置基线 s | 5 | — | — |

> `start_confirm` 单独说三遍：**它是最敏感的一个数**。
> 现场 ROI 仅约 1000 px²，实测 4130 帧里占比在阈值上下翻转 160 次、最长连续满足只有 0.54s。
> 用它来"求稳"必然把起判推后几十秒；要稳请用 `median_frames`。

## 5. 现场踩过的坑（都是真事故）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 起判晚 76s，90.47s 的反应算成 14.50s | 网页上把 `start_confirm` 改成 1.5 | 回归用例钉死 0.2；改参数走「备份→改→回读→观察下一炉」 |
| 2 | 一炉被切成两条（6.0s + 92.7s） | 中间熄 1.48s 超过结束确认 | `merge_gap=5` 断点续接，曲线接回 |
| 3 | 开门杂光被当成一炉 | 阈值法分不清杂光与真反应 | `guard_window/peak` + `min_duration` |
| 4 | 分段时刻显示 1970 年 | "秒表秒"当"日历秒"渲染 | 只在接线口 `shift_segments()` 平移一次 |
| 5 | 时长 `102.47999999999999` 入库 | 浮点噪声 | 判定/入库/响应/前端四层统一 round |
| 6 | 滑窗比例法越调越差 | 窗口一长滞后 20~30s | 不再用，改因果中值 |
| 7 | 落盘后合并器读不到数据 | reactions.jsonl 改名/清空 | 固定文件名、只追加、永不自动删 |

## 6. 扩展点（想加判据时看这里）

- **新异常类型**：`judge.py` 加常量 + 在 `judge()` 里按优先级插入分支；
  **类型码要与后端 `SpheroidizationRecord` 对齐**，且 `fusion.PRIORITY` 要同步补
- **新判据需要新测量值**：`FrameMetrics` 加字段 → `RoiProbe.measure()` 填 → 逐帧 CSV 列尾追加（不改前 11 列）
- **不同产品的标准来源**：只改 `StandardPolicy.window()` 的三级回退顺序，不动上层
- **离线复现**：`python -m vpmin.cli --clock frame` 用帧号推进，同一视频跑两次结果一致
